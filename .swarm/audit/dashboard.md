# dashboard audit

Scope: the two visual surfaces. **(1) `ui/` Flask app** (`ui/app.py` + `ui/templates/index.html`) — the *pipeline* dashboard. **(2) agent-layer dashboard** (`agent-communication-layer/scan_dashboard.py` FastAPI + `dashboard_page.html` + `dashboard_bus.py` + `run_dashboard_demo.py` + `wave4_dashboard_e2e_check.py` + `static/fonts`) — the *scan* dashboard.

## Aligned with demo story

**Both dashboards already cover north-star steps 3-6** (inventory → shortfall → negotiation narration → approval → settlement), differently:

- **Scan dashboard (`scan_dashboard.py` / `dashboard_page.html`)** is the *negotiation-centric* surface. It renders two live MJPEG camera feeds (A=receiving, B=source), per-facility qty/percent/threshold readouts, an animated "transfer corridor", a Baymax voice console, the AWAITING_APPROVAL gate with Approve / Order externally / Reject buttons, and a live SSE "dispatch log". Data path: `POST /scan` (proxies camera workers) and `POST /scan-and-negotiate` → `dashboard_bus.push_trigger` (Redis `baymax:trigger`); FRONT picks it up via the poller in `run_dashboard_demo.py`, and milestones stream back over `baymax:narration` pubsub → SSE `/events`. Approve/Order/Reject → `POST /decide` → `baymax:decision` → `resume_after_admin_decision`. **This is the cleaner, closer-to-target architecture**: it never touches negotiation logic directly, only the Redis bus, so it already shares ONE engine with the agents (no duplicated logic). `wave4_dashboard_e2e_check.py` exercises this whole trigger→gate→settle→narrate wiring offline with a stub bus and asserts the gate surfaces + CONFIRMED terminal — a real, passing harness.

- **Pipeline dashboard (`ui/app.py` / `index.html`)** is the *forecast/pipeline-centric* surface. It renders the full 6-stage pipeline strip (Weather→Illness→WHO→Vision→Claude→Fetch.ai), live Redis cards for forecast, Claude reasoning (risk level + priority items + rationale), scenario, 3-hospital inventory grid w/ surplus, transfers stream, alerts stream, two camera-capture panels, AND a "Fetch.ai Negotiation Live" timeline with the same approval banner. Auto-refreshes `GET /api/state` (direct Redis read) every 3s; negotiation events via SSE `/api/narration`. It manages the Bureau as a **subprocess** (`run_dashboard_demo.py`) and bridges approvals to iMessage. **It is the only surface that already renders steps 2 and 7** of the north-star: Claude crisis/risk *reasoning* (the `reasoning:latest` card) and the *ingest loop* — `POST /api/refresh_who` already runs WHO + weather + illness + Claude (`run_who_update`) and writes Redis. That endpoint **is** the "Ingest Data" button, just mislabeled "Refresh WHO + Claude".

## Redundant / dead / off-track

- **The two dashboards substantially overlap and partly conflict.** Both render camera inventory, both render a negotiation timeline with an identical Approve/Order/Reject gate, both consume `baymax:narration`. They are NOT wired together: the scan dashboard reaches FRONT only inside `run_dashboard_demo.py`'s in-process pollers, while `ui/app.py` spawns `run_dashboard_demo.py` as a subprocess with `BAYMAX_DASHBOARD_PORT=8079` — meaning **the FastAPI scan dashboard also boots (on :8079) but is orphaned/unused** when driven from Flask. So in the Flask path you get a hidden second dashboard nobody looks at. Pick one canonical surface.
- **Two divergent SSE narration mechanisms.** `scan_dashboard.py` subscribes Redis pubsub *per browser connection* (`dashboard_bus.narration_events`). `ui/app.py` runs ONE background pubsub thread into an in-memory `_narration_log` and replays it on `/api/narration` — but that replay loop (`while True: ...time.sleep(0.4)`) **never breaks on client disconnect**, leaking a generator per closed EventSource, and **replays the entire log to every new subscriber** (so a fresh page re-streams stale events; `index.html` also opens an SSE on page load *and* on each Run, risking duplicate streams). Off-the-happy-path but real.
- **`_parse_negotiation_log` in `ui/app.py` (lines 592-618) is dead code** — defined, never called (superseded by the pubsub narration path).
- **`scan_dashboard.py` `/scan-and-negotiate` hardcodes a single item (`ITEM`/"Saline")** and only ever requests for "Hospital A" with `quantity=need`. It cannot express the north-star crisis→at-risk-item selection.

## Buggy / untested / risky

- **Naming/env mismatch (per the brief's frozen note).** `ui/app.py` docstring line 472 references `STOCKPILE_REDIS=1` but the code (correctly) sets `BAYMAX_REDIS=1` (line 97) — stale doc only, not a live bug. The root `README.md` uses `stockpile_*` / `STOCKPILE_*` names that exist nowhere in code (live truth is `baymax_*` / `BAYMAX_*`). The scan dashboard is the only one that honors BOTH `WORKER_A_URL` and `BAYMAX_WORKER_A_URL` spellings (lines 65-76); `ui/app.py` only honors `REDIS_URL`.
- **`ui/app.py` decision push uses `LPUSH` (line 199) while the poller `pop_decision` does `LPOP` (`dashboard_bus.py` line 64)** → LIFO, not FIFO. With one pending decision it's fine; with two queued (approve then reject) the order inverts. `push_trigger` has the same LPUSH-vs-LPOP mismatch (`app.py` line 209 vs `dashboard_bus.pop_trigger` LPOP). `scan_dashboard.py`/`dashboard_bus.push_*` correctly use RPUSH+LPOP. Low-severity for a demo (queue depth ~1) but it's a genuine inconsistency between the two trigger producers.
- **Scan dashboard SSE has no disconnect handling either**, but `narration_events()` does clean up in `finally` — better than the Flask path.
- **`scan_dashboard.py` reads `dashboard_page.html` once at import (line 87)** — editing the page requires a process restart. Minor.
- **No test covers `ui/app.py`.** `wave4_dashboard_e2e_check.py` only exercises the scan-dashboard bus wiring (and stubs `dashboard_bus` entirely, so it doesn't test `scan_dashboard.py`'s HTTP layer either — only the FRONT-side pollers + narration sink). The HTTP endpoints, SSE replay, and Bureau subprocess management are all untested.
- **`ui/app.py` runs the camera capture (`api_capture`) with `sys.executable`** (the Flask venv), not the hardware venv — capture will fail unless deps happen to overlap. Cross-track fragility.

## Dependencies on other tracks

- **Redis track (`redis/`, `tracks/redis`):** both dashboards read/write the same keys — `forecast:{region}`, `reasoning:latest`, `hospital:{id}:inventory|surplus|meta`, `scenario:heatstroke`, `vision:latest`, `vision:image:{hid}`, `transfers` + `alerts:log` streams, and the bus lists `baymax:trigger`/`baymax:decision` + channel `baymax:narration`. Any key rename breaks the UI.
- **Agent/negotiation track (`baymax_agents.py`):** the dashboards depend on `register_narration_sink`, `start_negotiation(source="dashboard")`, `resume_after_admin_decision`, and the `AWAITING_APPROVAL` gate surfacing for `source=="dashboard"` (baymax_agents.py line ~290). The narration payload contract (`state`, `detail`, `req_id`, `final`) is the UI's wire format.
- **Vision/hardware track:** scan dashboard proxies `camera_worker.py` `/scan` + `/stream`; `ui/app.py` shells out to `hardware/camera connection/capture_single.py` and reads `vision:image:{hid}`. Capture runs under the wrong interpreter (`sys.executable`).
- **Forecast track (`fetch/agents/{who,weather,illness}_agent`):** `ui/app.py` `/api/refresh_who` imports `fetch.agents.who_agent.fetcher.run_who_update` (already aggregates WHO+weather+illness+Claude). **This is the existing ingest engine the north-star "Ingest Data" button needs — wire to it, don't rebuild.** Illness is still a mock feed; CDC is a stub (per north-star step 7).
- **Settlement / iMessage:** `ui/app.py` imports `fetch.approval.imessage_client.notify` for approval links.
- **MISSING — research/crisis seam:** no `research_crisis` seam exists in `interfaces.py` (confirmed: only inventory/rank/supplier/release seams). North-star steps 1-2 (crisis prompt → Claude infers crisis type + ranked at-risk supplies) have **no backend today**. The Claude `reasoning:latest` card is the nearest existing artifact but is WHO-driven, not crisis-prompt-driven.

## Open questions for the lead

1. **Which dashboard is canonical?** Recommendation: **`ui/` Flask app is canonical** (it already has the pipeline, Claude reasoning, the ingest engine, and the only path to north-star steps 2 & 7) — but **port `dashboard_page.html`'s visual polish + transfer-corridor + Baymax-voice console** onto it, and keep `dashboard_bus.py` as the shared engine seam. The FastAPI scan dashboard then becomes redundant; cut it (or demote to a camera-only viewer) to avoid the orphaned :8079 instance and the duplicated approval/SSE logic.
2. **Crisis prompt backend:** where does the new `research_crisis` seam live — a new function in `interfaces.py` delegating to a Claude call, surfaced via a new `POST /api/crisis` that writes `reasoning:latest` (or a new key) and optionally auto-triggers `start_negotiation` on the top at-risk item? This is the single biggest missing piece for steps 1-2.
3. **"Ingest Data" button:** relabel `/api/refresh_who` → "Ingest Data" and add the matching chat command, or add a thin `/api/ingest` alias? The engine already exists; this is mostly UI + a chat-intent route in `front_agent.py`.
4. **SSE strategy:** standardize on ONE narration transport. The Flask in-memory-replay path has a generator leak and replays stale events; the FastAPI per-connection pubsub is cleaner — adopt that pattern in Flask.
5. **Trigger/decision queue direction:** confirm RPUSH+LPOP everywhere (fix `ui/app.py`'s LPUSH) so the bus is FIFO before the demo queues multiple decisions.
